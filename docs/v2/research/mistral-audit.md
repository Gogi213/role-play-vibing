# ИИ-команды: рынок, бестпрактис и аудит role-play-vibing

## Вопрос

Как рынок и лучшие практики управления командой ИИ-агентов (2025–2026) соотносятся с проектом [role-play-vibing](https://github.com/Gogi213/role-play-vibing); почему проект может систематически ошибаться и не выполнять бизнес-задачу владельца; и какая альтернатива закроет задачу «владелец ставит цель → получает проверенный результат, без микроменеджмента».

## Резюме

1. **Главное расхождение с отраслевым консенсусом — передача контекста.** Принцип №1 по Cognition: между агентами нужно делить полные трассы, а не выжимки; иначе каждое действие несёт неявные решения, которые конфликтуют с решениями соседа — это и есть «хожу по кругу». С версии 1.8.46 каждая побудка роли в RPV — новая сессия, а память передаётся тикетом и блокнотом ≤ 4 КБ ([репозиторий](https://github.com/Gogi213/role-play-vibing)). Это конструктивный рецепт потери нити, повторения ошибок и «чиню → ломаю → чиню» — ровно провалы критериев 1, 6, 7 бизнес-задачи.
2. **Проект нарушил главный вывод Anthropic «Building effective agents» — «самое простое решение, усложнять только по необходимости».** RPV — это самодельная платформа: диспетчер на 166 КБ кода, собственная шина событий, веб-табло, присмотр ОС, система автовыпуска, ~40+ переменных окружения. Индустрия движется в обратную сторону: эти слои отдает платформа (Claude Code Agent Teams, Managed Agents, LangGraph + LangSmith).
3. **Критерий 16 «инструмент сам не становится проектом» провален с запасом и измеримо.** 63 релиза за 11 дней (1.0.0 от 03.10.2026 → 1.8.48 от 13.10.2026); тест одного диспетчера — 278 КБ, больше любого рабочего модуля. CHANGELOG — это хроника того, как инструмент чинил сам себя вместо бизнес-задачи.
4. **Сильные стороны RPV совпадают с тем, что реально работает по данным Cognition за 2026 год.** Судья = цикл «генератор–верификатор» с чистым контекстом ревьюера (их лучший рабочий паттерн); страж удаления; классификация вопросов владельцу (деньги | видимое | необратимое | бизнес-правило); шаблон brief, почти дословно повторяющий статью Anthropic про agent automations.
5. **«Множество ошибок» — не случайность, а три структурные причины:** (а) потеря контекста на каждом шаге; (б) лечение симптомов тормозами (лимиты возвратов, дедуп по difflib, «тормоза циклов») вместо причины; (в) самописность каждого слоя платформы, где каждый слой — свой источник багов (слепота диспетчера 54 мин, потеря событий spool, MSYS-пути, 3,3 млн токенов на «подогрев кэша»).
6. **Альтернатива есть и она дешевле.** Claude Code Agent Teams (экспериментальная штатная фича: общая задача-лист, прямые сообщения, lead-агент, дешёвые модели для исполнителей) закрывает ~60–70 % механики RPV; Managed Agents / облачные сессии закрывают «работу 24/7 без владельца» и «состояние в файлах». Кастомного кода хватает на метрики цикла. Судью — оставить как субагента-верификатора.

## Методология

- **Источники:** инженерные блоги Anthropic (4 статьи, включая указанную в задании), Cognition (2 статьи — «против» и «что работает»), LangChain (синтез обеих позиций), практические разборы паттернов 2026 года, независимый разбор Claude Code Agent Teams.
- **Аудит проекта:** README, уставы всех ролей, полный CHANGELOG (63 версии, читал целиком — он же источник данных об инцидентах), структура и размеры кода диспетчера, история коммитов (100+).
- **Ограничения:** систему не запускал вживую; выводы о поведении основаны на документации и CHANGELOG, где инциденты описаны самим владельцем. Численных метрик «время от цели до проверенного результата» ни в репозитории, ни у меня нет — критерии 3 и 11 оценены качественно. Официальные доки Agent Teams не открылись из моего окружения — фича оценена по независимому разбору с примерами вызовов.

### 3. Корневые причины «множества ошибок»

1. **Разрыв контекста на каждом шаге.** Роль просыпается в чистой сессии, видит тикет и блокнот ≤ 4 КБ. Все неявные решения предыдущих шагов (стиль, границы, что уже пробовали и не сработало) теряются. Cognition называет именно это причиной хрупкости мультиагентных систем. Отсюда повторные ошибки (критерий 7) и круги (критерий 1).
2. **Лечение симптомов, а не причин.** Циклы «чиню → ломаю» не устранены, а ограничены: потолок возвратов, после которого тикет закрывается «не сделано» (1.8.47). Это превращает проблему качества в проблему учёта.
3. **Самописная платформа = умножение поверхностей отказа.** Диспетчер + шина + сторож + присмотр + выпуск + табло — каждый слой пишет свой журнал, свои замки, свои тормоза, и на каждый в CHANGELOG приходится серия багов. Anthropic решает те же задачи на уровне платформы: Managed Agents дают расписание, хранилище памяти, бюджет, vault-доступы — и их не надо чинить владельцу.
4. **Нет петли обратной связи по бизнес-результату.** Ничто не измеряет «время от цели до проверенного результата» и «повторы одной ошибки». Метрики, которые есть (простой, токены), измеряют механику, а не результат. По Anthropic, без evals улучшение системы — вслепую.
5. **Знания о решениях владельца привязаны к сессии CEO.** Долгая сессия — единственное место, где живёт понимание «что владелец уже решил». Ротация сессии, `/clear`, падение Desktop — и критерий 6 требует повторения решений.

### 4. Что в RPV хорошо и не должно выбрасываться

- **Судья** — цикл generator–verifier с чистым контекстом и договором, зафиксированным до результата. По данным Cognition за 2026 год, ревьюер с чистым контекстом — лучший подтверждённый паттерн качества (в среднем ~2 бага на PR, ~58 % из них серьёзные).
- **Страж удаления** и правило «необратимое — только через CEO» (критерий 14 закрыт полностью).
- **Классификация вопросов владельцу** (`деньги|видимое|необратимое|бизнес-правило`) — точная реализация критерия 5.
- **Табло и сигнал «команда молчит»** (критерий 9 закрыт).
- **Шаблон brief** (1.8.43) — практически дословное следование статье Anthropic: закладки вместо фиксированных окон, «сбой источника ≠ тишина», перепроверка перед отправкой, предпочтения read-only.

### 5. Альтернативы

**Вариант A — рекомендация: платформа + минимум своего кода**

| Слой бизнес-задачи | Чем закрыть | Что даёт |
|---|---|---|
| Оркестрация: задачи, роли, кто кого будит | Claude Code Agent Teams (эксперим. фича) | Общая задача-лист (TaskCreate/TaskList/TaskUpdate с owner — аналог тикетов), прямые сообщения между агентами (нет односторонних `--next`), lead-агент, исполнители на дешёвых моделях |
| Проверка результата | Субагент-верификатор с чистым контекстом (аналог Судьи) + договор в тикете | Сохранить текущую сильную сторону RPV |
| Память: решения, предпочтения, «ошибка не повторяется» | Файлы проекта: CLAUDE.md, skills, memory-файлы; не сессия CEO | Решения владельца живут вне любой сессии; каждая роль их перечитывает (по Anthropic — «перечитывай предпочтения в начале каждого запуска») |
| Работа без владельца, расписания, фоновые задания | Облачные сессии Claude Code / Managed Agents | Не требует держать диспетчер на своей машине, состояние хранит платформа, бюджет на запуск — штатно |
| Необратимое | Разрешения и hooks Claude Code (pre-tool-use deny) вместо самописного стража | Тот же эффект без своего кода |
| Метрики (критерии 3, 11) | Тонкий слой своего кода: время цель→вердикт, токены на закрытую задачу, повторы ошибок | Единственное, что действительно стоит писать самому |

**Вариант B — если нужна полная кастомность:** LangGraph (durable execution: проверки точек, возобновление после падения — то, что RPV строил вручную) + LangSmith (трассировка каждого решения агента, evals, LLM-судья для скоринга). Это превращает самоделку в поддерживаемый продукт, но не снимает главный вопрос — нужен ли мультиагент вообще.

**Вариант C — минимальный:** один сильный агент с компакцией памяти (однопоточный писатель, субагенты только для чтения/ревью). По Cognition, это «пройдёт очень далеко» и именно это их производственный дефолт.

## Открытые вопросы

1. Нет численных данных о циклах RPV: сколько времени занимает «цель → проверенный результат», сколько повторов одной ошибки. Без этого любой вердикт о критериях 3 и 4 — оценочный.
2. Agent Teams — экспериментальная фича: пригодность для 24/7-работы без присмотра не доказана публично.
3. Совместим ли «Судья по договору» со субагент-моделью (договор должен записываться до исхода — это процесс, а не только промпт)?
4. Не исследовано: поведение RPV на реальном проекте после 1.8.46 (переход на фреш-сессии) — сам владелец считает его упрощением; если в реальности качество не упало, тезис о контексте слабеет.

## Рекомендации / Следующие шаги

1. **Заморозить механику.** Объявить 2 недели без изменений инструмента; измерить три числа: время «цель → принятый Судьёй результат», токены на закрытую задачу, повторные ошибки одного класса. Это база для любого решения.
2. **Пилот Agent Teams на одной реальной задаче.** Lead = текущий CEO, исполнители на дешёвой модели, Судья — субагент с чистым контекстом. Сравнить с RPV по тем же трём метрикам.
3. **Перенести память решений из сессии CEO в файлы** (CLAUDE.md / skill / memory-файл, который роли перечитывают). Это закрывает критерии 6 и 7 дешевле любого кода.
4. **Убрать тормоза, оставить метрику.** Потолки возвратов, дедупы, «тормоза циклов» — симптом-менеджмент; их должна заменить петля: замер цикла → один системный фикс → повторный замер.
5. **Не параллелить писателей.** Если останется мультиагент — пишет всегда один (Инженер в непрерывной сессии или с полной передачей трассы), остальные только читают и ревьюят.
6. **Расписание и фон — платформе** (облачные сессии / Managed Agents), а не самописному диспетчеру на своей машине: это одновременно закрывает критерии 10, 15 и убирает целый класс багов из CHANGELOG.
