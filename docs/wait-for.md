# Ожидания тикета (`wait_for`)

Долгую работу не держат сессией: тикет переводят в `status: waiting` с условием `wait_for`, а диспетчер сам проверяет условие и будит владельца тикета, когда оно выполнено.

## Формы условия

| форма | выполнено, когда |
|---|---|
| `host:<алиас>:<путь>` | файл по пути есть на машине (по ssh). Алиас — любое имя из `~/.ssh/config` (буквы, цифры, `.`, `_`, `-`; не с дефиса). Путь абсолютный (`/…` или `~/…`) |
| `host:<алиас>:unit:<имя>` | юнит systemd на машине не активен (остановился). Упал он или кончился успешно, форма не различает — для заданий лучше файл итога |
| `file:<путь>` | файл есть локально |
| `ticket:<ID>` | указанный тикет дошёл до `status: done` |
| `ci-run:<владелец/репо>#<id прогона>` | конкретный прогон CI завершён (успех или красный — исход смотрит владелец). Прогон исчез (404) — сторож будит владельца. Нужен, когда ждёшь прогон, а не голову PR (`ci:`) |
| `job:<алиас>:<id>` | задание проекта завершилось (`done`); упало/исчезло — сторож будит владельца с хвостом лога. Состояние даёт адаптер `RPV_JOB_STATE_CMD` |
| `at:<время ISO>` | наступило время (без пояса — местное). Суточные наблюдения: сторож жизни такие ожидания не будит и не считает зависшими. Метка-файл и задание планировщика не нужны |

Файл хода `*.json` (`{"done": N, "total": M, …}`) считается готовым при `done >= total`. Файл итога `*.rc` (его пишет `tools/jobrun.sh`) готов, как только появился; его текст диспетчер читает и кладёт в лог тикета.

Условие и статус ставит одна команда:

```
python <плагин>/.claude/dispatcher/tickets.py --project <проект> wait <ID> <условие> --by ЧЧ:ММ [--on-met ...]
```

Форма проверяется при записи. Срок `--by` (GMT+4) обязателен для `host:`, `file:` и `job:`: он выходит, а условие не выполнено — через 15 минут сторож будит владельца ([reliability.md](reliability.md)).

## Машины

Любая машина, до которой есть `ssh <алиас>` без вопросов: адрес, пользователя, ключ, `known_hosts` и прыжковый хост берёт сам `ssh` из `~/.ssh/config`. Плагин своих переменных для хостов и ключей не имеет. Вызов идёт с `BatchMode=yes` и `ConnectTimeout=8` — нужен ключ без парольной фразы (или ssh-agent). Алиас, которого нет в `~/.ssh/config`, ведёт себя как недоступная машина: условие «не выполнено», строка в `dispatch.err.log`, а при молчании дольше `RPV_BLIND_ALERT_S` — тревога «диспетчер слеп». Удалённая сторона — Linux или macOS: проверки выполняются командами `test`, `cat`, `systemctl`, `grep`.

## Как диспетчер узнаёт, что условие выполнено

- Первая проверка нового условия идёт сразу, затем сверка раз в `RPV_DISPATCH_WAIT_RECON_S` (300 с) — один ssh на машину проверяет все ждущие условия этой машины. Конец задания виден не позже чем через пять минут. Всё это делает поток `wait-poller`, тик диспетчера ssh не ждёт.
- Условие закрылось — владелец тикета просыпается. Если ждали файл итога (`*.rc`), в лог тикета ложится запись диспетчера с его текстом; упавшее задание помечено явно.
- Сторож (`watch.py`) разбирает мёртвые цели без модели: хост недоступен, файла нет и никто его не производит, срок `--by` вышел — и считает застой.
- Исходы ожиданий внешних заданий (`host:`, `file:`, `job:`) диспетчер и сторож дописывают в `.claude/dispatcher/jobs.jsonl` — по строке JSON на исход: `{"ts", "ticket", "wait_for", "outcome": "met"|"overdue", "rc": <текст файла итога | null>}`. `met` — условие закрылось, `overdue` — срок вышел и сторож разбудил владельца. Одна строка на (тикет, условие, исход). Ежедневный отчёт считает по ним «кончилось / потеряно».

## Задание на машине: `jobrun.sh`

`tools/jobrun.sh` запускает задание так, чтобы его конец и исход не терялись. Скрипт один раз копируют на машину (он ничего больше не требует: bash, `systemd-run` — если есть).

1. На машине: `ssh <алиас> 'RPV_RUNS_DIR=/var/lib/rpv/runs /opt/bin/jobrun.sh <метка> -- python run.py --all'` печатает `UNIT=<метка>-<runid> RC=<путь к файлу итога>`. Метка и `runid` дают уникальное имя; два запуска с одной меткой не путаются.
2. С systemd скрипт запускает задание транзиентным юнитом (`systemd-run --collect`), а итог пишет его `ExecStopPost`; без systemd (macOS, контейнер) — фоновая оболочка с `trap`, вывод задания идёт в `<unit>.log` рядом с файлом итога. Режим выбирается сам, `RPV_JOBRUN_MODE=systemd|trap` задаёт его явно. Дополнительные свойства юнита — `-p СВОЙСТВО` до `--`.
3. Тикет ждёт файл итога: `tickets.py wait <ID> host:<алиас>:<путь RC> --by ЧЧ:ММ`.
4. Когда задание кончилось, появляется `<RPV_RUNS_DIR>/<unit>.rc` — целиком, через временный файл и `mv`. В нём одна строка: `SERVICE_RESULT=success EXIT_STATUS=0` — успех; `SERVICE_RESULT=exit-code EXIT_STATUS=2` — код выхода; `SERVICE_RESULT=signal EXIT_STATUS=TERM` — убито сигналом.
5. Диспетчер видит файл при ближайшей сверке (≤ 5 мин), пишет его текст в лог тикета и будит владельца. Задание, убитое вместе с машиной, итога не оставляет — его ловит срок `--by`.

Каталог итогов — `RPV_RUNS_DIR` (по умолчанию `/var/lib/rpv/runs`); пользователю юнита нужна запись в него.

## `on_met`

`--on-met "python tools/x.py арг"` — когда условие выполнено, диспетчер сам запускает эту команду вместо пробуждения роли. Допустимы `python`, `python3` или `bash` и скрипт под `tools/` или `.claude/` проекта, отслеживаемый git (пути с прямыми слешами). Результат пишется в журнал тикета. Отказ, сбой или таймаут (`RPV_DISPATCH_ON_MET_TIMEOUT_S`, 120 с, дерево процессов убивается) — диспетчер будит владельца тикета; то же после трёх `on_met` подряд без запуска роли. `on_met` не закрывает тикет и не зовёт Судью: такой тикет возвращается в `in_progress`. После таймаута запуска роль продолжает **ту же сессию** (`--session-id`).

## Защита от циклов

`tickets.py wait` отказывает, если `ticket:<ID>` замыкает цепочку ожиданий: каждый ждёт следующего, и никто не пойдёт. Уже существующий цикл диспетчер сообщает CEO раз в сутки. Ждите результат (`file:`, `host:…`), а не тикет, или разорвите цепочку.

Тикет в `waiting` без условия и без `--next` диспетчер не оставляет: через 10 минут это считается простоем, а владельца тикета диспетчер будит сам — см. [reliability.md](reliability.md).
