# Настройка

Настроек у плагина три вида, и каждое значение живёт ровно в одном месте:

| где | что | кто меняет |
|---|---|---|
| [окружение машины](#окружение-машины) | четыре переменные: где проект, бот владельца, папка плагина для проверки | владелец на своей машине |
| [файл проекта `.claude/rpv.json`](#файл-проекта-clauderpvjson) | всё, что зависит от проекта: защищённые пути, машины, пределы параллели, время отчёта, автовлив PR | CEO командой `tickets.py config set` (ниже); прямая запись закрыта стражем всем |
| [константы в коде](#константы) | пороги и периоды механики (тик, таймауты, тормоза цикла, сторож) | только выпуском плагина |

Пустое значение считается «не задано». Проверка, что этот документ совпадает с кодом, — тест `test_configuration_doc.py`.

## Окружение машины

| переменная | по умолчанию | смысл |
|---|---|---|
| `RPV_PROJECT` | — | корень проекта; порядок поиска: `--project`, `RPV_PROJECT`, `CLAUDE_PROJECT_DIR`, ближайший каталог вверх от текущего с `.claude/roles` |
| `RPV_TG_TOKEN` | не задан | токен бота владельца от @BotFather: ежедневный отчёт, тревога «работа стоит» и ваши вопросы (по сообщению на вопрос). Не задан (или не задан чат) — Telegram не настроен: сообщения не уходят, строка «не отправлено» в `notify.log`, отчёт всё равно пишется в `.claude/dispatcher/reports/<дата>.md` |
| `RPV_TG_CHAT` | не задан | идентификатор чата владельца (число из `getUpdates` после первого сообщения боту) |
| `RPV_PLUGIN_DIR` | — | папка плагина для ролей (`claude --plugin-dir`, перекрывает установленный): проверка рабочей копии на чистом проекте, `tools/e2e_clean_project.py` |

Токен и чат — в окружении, а не в файле проекта: секрет не должен попасть в репозиторий. Проверка связи: `python <плагин>/.claude/dispatcher/notify.py --project <проект> test`.

Кроме них плагин читает переменные Claude Code: `CLAUDE_BIN` (путь к CLI, по умолчанию `claude` из `PATH`), `CLAUDE_PROJECT_DIR`, `CLAUDE_CONFIG_DIR`.

Службу запускает `/rpv-start` (`start.py`): она получает только `RPV_*`, `CLAUDE_BIN`, `CLAUDE_PROJECT_DIR`, `CLAUDE_CONFIG_DIR` и `PATH` (на POSIX); секреты (`ANTHROPIC_*`, токены) не переносятся. Присмотр ОС запоминает `RPV_*` и `CLAUDE_*` в `supervise.env.json` без секретов — [reliability.md](reliability.md#присмотр-за-диспетчером-и-сторожем).

**На удалённой машине** — переменные `tools/jobrun.sh`, их задают там, в окружении запуска скрипта ([wait-for.md](wait-for.md#задание-на-машине-jobrunsh)):

| переменная | по умолчанию | смысл |
|---|---|---|
| `RPV_RUNS_DIR` | `/var/lib/rpv/runs` | куда `jobrun.sh` пишет файл итога задания `<unit>.rc` (и `<unit>.log` без systemd) |
| `RPV_JOBRUN_MODE` | сам: `systemd`, если есть `/run/systemd/system` и `systemd-run`, иначе `trap` | режим запуска задания: юнит systemd с `ExecStopPost` или фоновая оболочка с `trap` |

**Служебные** — их ставит сам плагин, руками не задают: `RPV_ROLE` и `RPV_TICKET` (роль и тикет запуска; диспетчер — дочернему `claude`, хуки по ним вставляют устав и ведут конспект). Запуск роли их не меняет и не стирает — страж отказывает; а если окружение всё же стёрто из скрипта, роль узнаётся по дереву процессов (`project.caller_role`: процесс внутри запуска роли из `state.json`), так что притвориться CEO для реестра решений, согласия на публикацию и исправления ошибки нельзя, `RPV_START_CMD` и `RPV_START_CWD` (`start.py` передаёт команду и каталог процессу WMI на Windows).

## Файл проекта `.claude/rpv.json`

Один объект JSON в проекте. Файл, а не переменные, — чтобы настройка ехала вместе с проектом: в репозитории, на другой компьютер и в другой клон. Нет файла или ключа — значение по умолчанию. Правка действует без перезапуска служб (файл перечитывается по времени изменения). Файл не правят руками ни роль, ни CEO (страж отказывает): CEO меняет его командой `tickets.py config set <ключ> <значение> --why "..." [--ref В-N]` — только ключи из таблицы ниже и только допустимые значения (неизвестный ключ или значение — отказ). Каждая правка — строка журнала `.claude/dispatcher/config-log.json` (время, было → стало, зачем, слово владельца из реестра по `--ref`), Судье сама заводится проверка; не принятая им (`tickets.py config accept CFG-N`) правка откатывается к прежнему значению через 2 ч (`rpv_config.ROLLBACK_AFTER_S`, откат делает сторож). В ежедневном отчёте — раздел «CEO изменил работу команды» (нет правок — нет раздела). Уставы `.claude/roles/*.md` CEO не правит ни одним способом — `cp`, `mv`, `tee`, `>`, `python`, `sed -i`, Write/Edit (кроме строк таблицы зон в README); новые строки уставов после выпуска плагина переносит команда `tickets.py charter sync [--file <имя>.md] [--why "..."] --ref В-N` (без `--ref` отказ: слово владельца сначала в реестр): файлы из `templates/roles/` установленной версии плагина кладутся в `.claude/roles/` как есть, строки таблицы зон README, уже стоящие в проекте, остаются проектными; перенос — строка журнала `.claude/dispatcher/charter-log.json` и строка раздела отчёта «CEO изменил работу команды»; строки, которые перенос убрал из устава проекта и которых нет в шаблоне, команда выводит списком «перенеси нужное в добавку» и пишет в запись журнала (`removed`); правила проекта для роли лежат в добавке `.claude/roles/project/<роль>.md` (и `project/README.md`) — `tickets.py charter addon <роль|README> --text "..." [--replace] [--why "..."] --ref В-N` дописывает текст (или заменяет файл), переносы её не трогают, хук запуска роли кладёт добавку в контекст сразу после устава (не влезла — путь), запись — в журнал и в тот же раздел отчёта, руками страж её закрывает как устав (и новый файл тоже); блокнот `notes/ceo.md` — свободно. Сломанный файл (не JSON) исправляется руками.

```json
{
  "protected_paths": ["data/raw/**", "backups", "*.pem"],
  "report_at": "09:30",
  "max_parallel": 3,
  "role_parallel": {"engineer": 2},
  "role_mcp": "none",
  "ci_repo": "owner/repo",
  "watched_aliases": ["gpu1"],
  "job_state_cmd": "jobstate {id}",
  "job_owners_cmd": "jobowners",
  "stray_cmd": "jobstrays"
}
```

| ключ | по умолчанию | смысл |
|---|---|---|
| `protected_paths` | нет — защиты нет | шаблоны путей, которые не удаляет и не перезаписывает никто ([ниже](#защищённые-пути)) |
| `report_at` | `10:00` | время ежедневного отчёта владельцу, `ЧЧ:ММ`, местное время машины диспетчера. Не разобрать — `10:00`. Диспетчер стоял в это время — отчёт уходит на первом тике после и один раз |
| `max_parallel` | `3` | сколько запусков ролей одновременно (целое ≥ 1) |
| `max_runs_per_ticket_hour` | `12` | сколько раз за час диспетчер запускает роли по одному тикету (целое ≥ 1); выше предела тикет ждёт, ошибки нет, но время идёт в простой |
| `role_parallel` | по одному на роль | предел запусков по ролям, `{"engineer": 3, "researcher": 1}`; на один тикет — всегда один запуск роли; пара не «роль: целое ≥ 1» пропускается с предупреждением |
| `judge_scale_queue` | `2` | очередь сдач на приёмку (тикеты, ждущие запуска Судьи, без идущего запуска Судьи и не придержанные троттлингом запусков), с которой разрешён второй Судья (целое ≥ 1); ниже порога — один Судья, выше — не больше `role_parallel.judge` (без записи предела — один). Очередь упала — идущий запуск не снимается, новый второй не стартует. Решение (разрешён/не нужен, с числом идущих Судей) — одной строкой в `dispatch.run.log` при смене, на паузе лимита не пишется |
| `role_mcp` | `all` | MCP-серверы ролей: `all` — как у обычного `claude`; `none` — ни одного (экономия памяти); список имён — только эти из `~/.claude.json` и `.mcp.json` проекта |
| `ci_repo` | нет — автовлива нет | `владелец/репо`: включает службу `ci_watch` (автовлив PR при вердикте Судьи, без ожидания CI (TK-139); красный CI на основной ветке — тикет «Починить CI») и репозиторий по умолчанию для `accept --pr` |
| `watched_aliases` | нет | ssh-алиасы машин, где сторож гоняет адаптеры заданий `job_owners_cmd` и `stray_cmd` |
| `job_state_cmd` | нет — форма `job:` не проверяется | адаптер формы `wait_for: job:<алиас>:<id>`: команда с `{id}`, выполняется по ssh на машине алиаса; 1-я строка вывода `running\|queued\|done\|failed\|missing`, далее хвост лога. Падение будит владельца тикета сразу; `missing` — после двух проверок подряд; причину по хвосту лога одной строкой пишет Haiku |
| `job_owners_cmd` | нет | адаптер «чьё задание»: строка на задание, поля через TAB — id, тикет, юнит, состояние, причина |
| `stray_cmd` | нет — проверки нет | адаптер «прогон мимо планировщика поверх чужого задания»: строка `тикет<TAB>описание`; сторож будит владельца тикета, без тикета — CEO; о том же прогоне — не чаще раза в 2 ч |
| `hold_alive_waits` | `true` — роль на `waiting` с невыполненным `wait_for` не запускается, пока сторож видит задание живым | `false`: прежнее поведение — `next:` и просрочка срока будят роль и при живом задании. Живое — юнит/процесс с именем задания, задание тикета в адаптере (`running`/`queued`); срок `--by` при живом задании будит не раньше чем через 12 ч после срока; отметка сторожа (`wait-alive.json`) старше 15 мин не действует (TK-054) |
| `release_dead_waits` | `true` — `waiting` на то, что уже не наступит, диспетчер снимает сам: `next` = владелец тикета, запись dispatcher «ожидание X не наступит: причина» | `false`: прежнее поведение — такой тикет ждёт молча. Что считается не наступившим: `ticket:<ID>` — цель в статусе `stopped` либо `done` без результата — только по положительному признаку: последний вердикт Судьи «вернуть» без приёмки после него, либо CEO закрыл записью `[итог: done]` с «не сделано», а Судья не принимал (у тикетов с ревьюером; нет записи «принять» в формате — не признак); `merged:`/`ci:` — PR закрыт без слияния (запрос к GitHub раз в 5 мин на тикет). `file:` без писателя (файла нет, локального процесса с путём, именем файла или «каталог/имя» нет, `DEAD_WAIT_STRIKES` проверок подряд; голое имя короче 4 знаков без каталога не различимо — не снимается), задания и процессы (`job:`, `host:`, `ci-run:`) ведёт сторож. Владельца-роли нет — строка CEO `wait-for`, тикет не трогается (TK-124, В-61) |
| `role_turns` | `true` — диспетчер сам отдаёт ход роли вместо строки CEO: `--next ceo`, передача CEO без ответа, цикл ожиданий, хвост приёмки → Судья; `нет-хода` → владелец тикета | `false`: прежнее поведение — строка в очереди CEO, ход за CEO. Не больше 3 записей «Ход тебе» на вид в одном тикете; передача от самого Судьи остаётся за CEO (TK-127, В-63) |
| `watch_unreleased` | не указан — включён там, где задан `ci_repo`; нет `ci_repo` — сигнала нет | ровно `false` выключает (строка `"false"` тоже выключает; ровно `true` — как не указан): сторож кладёт в очередь CEO строку `watch-unreleased` и будит CEO событием, когда тикетов в работе (`todo`, `in_progress`, `in_review`, `waiting`, `blocked`, `needs_owner`) нет дольше 10 мин, а у GitHub в основной ветке (`default_branch`) репозитория `ci_repo` есть коммиты после последнего тега `v*` (старший по номеру; локальный `main` не смотрится), и среди изменённых файлов есть не только `docs/` и `tools/`. Повтор — раз в сутки, пока не выпущено; нет `ci_repo` — молчит; GitHub не ответил — молчит и метку суточного повтора не снимает (TK-062, TK-072, TK-110) |
| `goal_idle_min` | `10` | целое ≥ 1, минуты: через сколько после приёмки шага открытой цели (`G-NNN`) без открытого тикета на неё сторож будит CEO сигналом `watch-goal-idle`; тот же срок — для тикета, принятого с `--tail ceo:`, пока на хвост не заведён тикет; один раз на событие (TK-086) |
| `pulse_dead_min` | `2` | целое ≥ 1: минуты тишины с конца прошлого тика, после которых Пульс считает диспетчер молчащим (`dispatcher_dead`; долгий тик не в счёт) (TK-095, docs/pulse.md); менять — Судья |
| `pulse_unserved_min` | `20` | целое ≥ 1: минуты: тикет в очереди, слот свободен, а запуска нет (`unserved`) — столько терпим (таймаут запуска) (TK-095, docs/pulse.md); менять — Судья |
| `pulse_ci_red_min` | `30` | целое ≥ 1: минуты: PR сдан, CI красный или конфликт с веткой по умолчанию (`ci_red`; закрытые PR не считаются) (TK-095, docs/pulse.md); менять — Судья |
| `pulse_loop_returns` | `2` | целое ≥ 1: число возвратов Судьи, с которого тикет в петле (`loop`) (TK-095, docs/pulse.md); менять — Судья |
| `pulse_loop_errors` | `2` | целое ≥ 1: число упавших запусков одного тикета в окне, с которого он в петле (`loop`) (TK-095, docs/pulse.md); менять — Судья |
| `pulse_loop_window_min` | `60` | целое ≥ 1: окно в минутах для `pulse_loop_errors` (TK-095, docs/pulse.md); менять — Судья |
| `pulse_move_warn_min` | `15` | целое ≥ 1: минуты без движения у текущего шага плана цели (последняя запись лога тикета или запуск роли), с которых метка-таймер Пульса пишет «стоит N мин» жёлтым (TK-108, docs/pulse.md); менять — Судья |
| `pulse_move_bad_min` | `30` | целое ≥ 1: то же, красным (TK-108, docs/pulse.md); менять — Судья |
| `has_ci` | `true` — на PR проекта есть CI | `false`: CI на PR нет, поэтому устав не отсылает полный прогон к нему — полный прогон тестов проекта остаётся обязанностью роли и пишется в её отчёт «Итог» (не в команду ярлыка договора; приёмка по-прежнему гоняет только тесты самой правки; отказ на полный прогон в договоре не отсылает к CI). При `false` хук запуска кладёт ролям (кроме CEO) строку «CI на PR нет» (TK-080), а автовлив (`ci_repo`) вливает PR по вердикту Судьи на текущей голове и «сливаем» от GitHub (TK-083); с TK-139 (В-72) CI слияния не ждёт и при `has_ci: true`: красный CI на сданном PR — запись в тикет, красный на основной ветке — тикет Инженеру «Починить CI»; запись приёмки по умолчанию не требует CI, а `wait`/`result wait` с `ci:<репо>#<PR>` отказывают («нет CI, ожидание не снимется») — жди `merged:<репо>#<PR>` (TK-084) |
| `ceo_wake` | `true` — диспетчер будит CEO событием | `false`: побудки нет, остаются строки `ceo-inbox.md` (TK-085) |
| `ceo_wake_mode` | `bypassPermissions` | режим разрешений headless-запуска побудки (`claude -p --permission-mode`); обязан совпадать с режимом сессии CEO, иначе сообщение повисает на одобрении и не будит (TK-085) |
| `tail_fields_only` | `false` — хвосты ищутся во всей сдаче | `true`: детектор хвостов приёмки читает только поле `--left "что осталось"` сдачи (`result done|pr`; `-` = ничего), а не свободный `--why`; сдача исполнителя без `--left` — отказ (TK-089) |
| `require_probe` | `false` — `wait` как раньше | `true`: ожидание вида из `probe_kinds` (умолчание `host:`/`job:` — расчёт на сервере; `file:` пробы не требует) со сроком `--by` дальше `probe_threshold_min` принимается только с `--probe <запись|файл>` (G-008): ≥ 2 способа (один «как есть») — в строке время (сек|мин|ч) и пик памяти (МБ|ГБ) на малом срезе; строка «тяжёлый: <элемент> · пик <МБ|ГБ> одного процесса» (G-009); строка «N: <число параллельных процессов>»; строка «оценка: N мин|ч»; срок не короче оценки. Проба — один раз на тикет: пишется в шапку `probe:` и в лог, дальше `wait` идёт без неё. Форму проверяет код, содержание — Судья |
| `probe_threshold_min` | `15` | минуты: ожидание ближе порога пробы не требует; считается сумма сроков `--by` всех `wait` одного расчёта без пробы (шапки `probe_waited:`, `probe_waited_at:`), нарезка коротким `--by` порог не обходит; после `[итог: done]` или `[итог: accept]` в логе счёт начинается заново; целое ≥ 1, действует при `require_probe: true` |
| `probe_kinds` | `["host", "job"]` | виды `wait`, которым нужна проба: `host`, `job`, `file` (список из них, не пустой); `file:` по умолчанию без пробы — ожидание файла не расчёт; действует при `require_probe: true` |
| `host_free_cmd` | нет — проверяется только форма записи пробы | `require_probe: true`, G-009: команда проекта, по ssh на машине алиаса из `host:`/`job:`, печатает первой строкой `<свободные ядра> <свободные ГБ>` (в шаблоне обязателен `{ticket}` — `config set` без него отказывает — чтобы не считать процессы самого тикета). `wait` отказывает, если N больше свободных ядер или N × пик × `host_mem_reserve` больше свободной памяти, и называет `N_max = min(ядра, память ÷ (пик × запас))`; при N меньше `N_max` пишет в журнал «можно больше». Не ответила — `wait` проходит, в журнале пометка. После OOM-kill задания тикета (сторож видит по причине падения) следующий `wait` тикета требует `--probe` с другим пиком или меньшим N, иначе отказ |
| `host_mem_reserve` | `1.2` | запас к пику памяти процесса при проверке `host_free_cmd`; число ≥ 1 |

### Защищённые пути

| шаблон | что защищено |
|---|---|
| `deep`, `*.pem` | файл или каталог с таким именем на любой глубине (как в `.gitignore`) |
| `data/raw`, `data/**/secret` | путь от корня проекта; `*`, `?`, `[…]` — внутри одного имени, `**` — любое число каталогов |
| `/mnt/archive`, `~/keys`, `c:/data` | именно этот путь (`~` — домашний каталог) |

- Защищён сам путь и всё внутри. Каталог, в котором защищённое лежит, при удалении тоже закрыт (`rm -rf data` при `data/raw`), если шаблон начинается с пути; шаблоны-имена и `**/…` родителей не закрывают. Регистр не различается, хвостовой `/` не нужен. Маска в команде (`rm data/*`) считается «может задеть».
- Закрыты: удаление и перенос (`rm`, `mv` источника, `find -delete`, `rsync --delete`, `git clean`, `shutil.rmtree`, `Remove-Item` и подобные) и перезапись существующего файла (`>`, `tee`, `cp`/`mv` поверх, `truncate`, `dd of=`, Write/Edit/MultiEdit/NotebookEdit). Новый файл на этом месте ничего не затирает — можно; дописывание `>>` тоже.
- По ssh корень проекта неизвестен: шаблон с путём ищется на удалённой машине на любой глубине, абсолютный — как записан.
- В тексте отказа названы файл и шаблон, который сработал. Снять защиту может только CEO по слову владельца.

### Страж удаления

Хук `PreToolUse` (`hooks/hooks.json`) ловит Bash, PowerShell, Monitor, Write, Edit, MultiEdit и NotebookEdit: удалять и перезаписывать можно только внутри проекта и его worktree (`.claude/worktrees/*`), scratchpad сессии и временного каталога. Работает в проектах с `.claude/roles`. Читающие команды (`ls`, `cat`, `grep`, `git status|log|diff|show`, …) пропускаются до разбора. Команды `ssh`/`scp`/`rsync` и удалённые машины не разбираются. Правил конкретного проекта (каталоги данных, замки замеров) в плагине нет: что нельзя трогать, проект объявляет сам — ключом `protected_paths`.

`git reset --hard`, `git clean -f` и откат всего дерева (`checkout .`, `restore .`) страж пропускает только в worktree проекта и scratch; `git push --force`, удаление веток на удалённом (`git push --delete`, `:ветка`) и `git branch -D main|master` — никогда. Откат одного файла (`git checkout -- файл`) и `git branch -D` локальной ветки свободны.

## Машины и ssh

Машина в `wait_for: host:<алиас>:…` — любой алиас из `~/.ssh/config`: адрес, пользователя, ключ и `known_hosts` берёт сам `ssh`. Настроек для хостов и ключей у плагина нет ([wait-for.md](wait-for.md#машины)).
