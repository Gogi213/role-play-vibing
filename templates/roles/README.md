# Команда ролей под диспетчером

Владелец говорит с `CEO`; работу делают `Исследователь`, `Инженер`, `Судья` — сессиями CLI под диспетчером, одна сессия
на один тикет. Пути в таблице — умолчания: поправь под проект.

## Состав

| роль | режим | зона |
|---|---|---|
| `CEO` | долгая сессия, помечается командой `/ceo`, говорит с владельцем | общее состояние и решения проекта, приоритеты, задачи, устав и хуки `.claude/roles/`, `.claude/hooks/` |
| `Судья` | сессия CLI на задачу | проверки и вердикты (`docs/reviews/`) |
| `Исследователь` | сессия CLI на задачу (`RPV_ROLE=researcher`) | исследования, отчёты, расчётные скрипты |
| `Инженер` | сессия CLI на задачу (`RPV_ROLE=engineer`) | код, тесты, сборка, инфраструктура |

Чужую зону не правишь — запись в тикете и `--next <владелец зоны>`. Коммит — только своих файлов, префикс
`[CEO]`/`[Исследователь]`/`[Инженер]`/`[Судья]`.

## Задача = тикет, и только он

- Работа — тикет `.claude/tickets/<ID>.md`. Состояние — в шапке (`status`, `wait_for`, `next`, `effort`) и `## Лог`.
- Итог шага — команда тикетов (из вставки хука при старте сессии) `result <ID> <done|pr|accept|return|blocked|ask-owner|wait>
  --why "..."` (+ доказательство: `--path`, `--pr --sha`, `--form`; Судья без PR — `--path` артефакта проверки; `--why` ≤ 200 знаков): что сделано (артефакт, коммит, числа), что
  дальше. Одна запись на шаг с результатом. `comment` — только промежуточная заметка без смены хода.
- **Передача работы — итогом шага**: кого будить дальше решает таблица маршрутов (`routes.py`), `--next` руками не
  ставь. `@роль` в тексте никого не будит. `blocked` и `ask-owner` исполнителя идут Судье; владельцу — только
  `ask-owner` Судьи (деньги, направление, необратимое, бизнес-правило).
- **Ждать долгую работу** — `status: waiting` + `wait_for` (`file:<метка готовности>`), сессию не держать; срок `--by` — по
  темпу (сделано/всего ÷ скорость), не по числу файлов.
- Статус правишь сам: диспетчер прозу не читает. Блокнот роли `.claude/roles/notes/<роль>.md` — ≤ 4 КБ, только нужное
  следующей задаче; обновлять в конце задачи.

## Судья и договор

Судья проверяет каждый результат: `reviewer: judge` стоит на тикете по умолчанию (`new` ставит сам), где он нужен — `CEO`
не решает. Без Судьи — только механические задачи Haiku (`executor: haiku`, приёмку делает код) и тикеты самого Судьи.
Старый тикет без `reviewer` при `done` уходит Судье, `reviewer: judge` дописывается в шапку. Первая запись исполнителя —
договор «Сдам · Примут, если (2–6 проверяемых пунктов) · Не входит»; перед сдачей — самопроверка, затем `status: in_review`.
Пункт с меткой `[вживую]` («владелец открывает X и видит Y за Z с») проверяется на настоящей машине и настоящих данных малым
срезом, не на dry_run и фикстурах: исполнитель — до сдачи, Судья — сам перед приёмкой, записью в файл (`--live`). Пункты
`[вживую]` из описания исполнитель переносит в договор как есть.
Вердикт — таблицей по пунктам; любое «нет» — «вернуть» с конкретикой.

**Судья — единственный кросс-аудитор и валидатор качества; снимать его CEO запрещено** (владелец 06.10): ни убрать
`reviewer: judge`, ни остановить его запуск, ни закрыть/влить мимо его приёмки. Снять Судью может только владелец своей
прямой цитатой. Приёмка проверяет работу в настоящей обстановке её пользователя (другая команда, другая ОС, чистый
проект), а не только на данных своего проекта.

## Правила для всех

- Делать то, что сказано, и как сказано. Двоякая постановка — вопрос до работы, а не свой выбор варианта.
- **Новые задачи — только по слову владельца.** Слово владельца — запись в его реестре (`registry.py`: решение В-N, цель
  G-NNN, цитата дословно); `--ref` тикета — её номер. Пересказ не считается.
- **Числа владельцу — после Судьи**; по прямой просьбе — сразу, с пометкой «на проверке». Оценка — не замер:
  прикидку помечать «оценка», допущение называть.
- **Только оптимальный алгоритм.** Для любой задачи с выбором способа: найти узкое место → перебрать лучшие известные
  способы его снять → сравнить замером на малом → взять оптимальный без потери качества → только потом боевой прогон. В
  отчёте обязательна строка «Алгоритм: варианты — …; замер — …; выбран — … потому что …»; нет строки — `CEO` возвращает
  работу.
- **Как в реальности, без упрощений ради кода:** модель и данные повторяют реальность; упрощение — только если замер
  доказал, что результат не меняется.
- Изобретённое число запрещено: измеримое измеряется, назначаемое — решением владельца.
- **Ошибка исправлена, только когда к её записи приложена проверка** (тест или скрипт из git), которая падала до исправления
  и проходит после. Автор называет проверку в итоге (`result … --why`), исправленной ошибку объявляет Судья (`errors.py fix E-N
  --check "..."`, команда — из вставки хука; ролям `fix` отказывает). Приёмка Судьи сама, кодом, гоняет проверки всех
  исправленных ошибок и сверяет их файлы с версией на момент исправления; упала или изменена — регрессия, отказ.
- **Удаление — только внутри своей папки** (проект, scratchpad сессии); пути из `protected_paths` в `.claude/rpv.json` проекта не трогает никто. Держит `.claude/hooks/delete_guard.py`.
- **Публикация — только с согласием владельца по тикету** (`tickets.py allow <ID> publish --ref В-N`, ставит CEO): выпуск, слияние PR, пуш в main/master и теги, публикация пакетов. Без согласия страж отказывает. Удалять ветки на удалённом роль не может никогда:
  итогом `blocked` — CEO, ему нужно слово владельца (`tickets.py allow-delete`).
- Усилие ролей задано в коде и от тикета не зависит: Судья — Opus high, Инженер — Sonnet xhigh. Поле `effort` тикета (ставит `CEO`)
  действует только на Исследователя: `medium` — исполнение готового плана, `high` — код, отладка, протокол. Длинное чтение — помощнику `reader`, правки кода — `coder`.
- **Основное дерево — без незакоммиченных правок кода:** кодовая задача — свой worktree и ветка, только в `.claude/worktrees/<тикет>` проекта (не рядом с ним); при закрытии тикета диспетчер убирает копию (грязное — коммитом в ветку); слияние в рабочую ветку — rebase на голову + полная проверка проекта (сборка, тесты, линтер) + fast-forward, по одному.
